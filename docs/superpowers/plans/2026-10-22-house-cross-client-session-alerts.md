# House 공통 세션 알림·인계 연결 설계

작성일: 2026-10-22 KST

상태: 처음 작성한 설계안. 이후 사용자의 구현·시험 요청으로 0.4.2 개발본에 연결 기능을 구현했다.
설계 기준: House 0.4.1, feat/house-0.4.1-research, fd543019a189b3f607f66663306235121907e5bf.
현재 사용법과 구현 범위는 [연결 지침](../../../skill/references/connections.md)을 따른다. 아래 본문은 초기 제안과 검증 목표를 보존한다.

구현 검토 후 연결 우선순위를 조정했다. 등록만 확인하고 launcher 훅을 제거하면 native 신뢰 검토 전에는 관측 경로가 사라질 수 있다. 따라서 House가 실행한 CLI·웹은 invocation 훅을 유지하고, 그 프로세스의 project 훅은 수신만 하고 기록하지 않는다. 일반 클라이언트는 project 훅으로 기록한다. 두 경로는 같은 v2 엔진을 사용한다.

현재 등록은 컴퓨터별 로컬 바인딩이다. 기존 hooks 파일에도 명시적으로 병합하므로 팀 공유용 이동식 설정 분리는 후속 과제다. 실제 IDE·데스크톱 화면, Windows native 실행과 클라우드 원격 연결은 이 로컬 구현·자동 시험만으로 지원 확정하지 않는다.

## 1. 사용자에게 달라지는 동작

사용자는 VS Code의 Codex 확장, VS Code 내장 터미널의 Codex CLI, 독립 터미널 CLI, 데스크톱 앱 중 편한 곳에서 같은 프로젝트를 연다. 한 프로젝트에 한 번 등록한 연결을 지원되는 로컬 클라이언트들이 공유한다. House를 통해 Codex를 다시 실행하는 절차를 필수로 두지 않는다.

대화 상태를 관측할 수 있으면 동일한 기준으로 경고한다. 관측할 수 없으면 “알림 연결 안 됨”, “관측 정보 없음”, “신뢰 확인 필요”처럼 실제 상태를 표시한다. 경고가 없다는 이유로 세션 상태가 양호하다고 해석하지 않는다.

여기서 앱은 Codex 작업을 하는 데스크톱 앱을 우선 뜻한다. 클라우드가 대화를 운영하는 앱·웹은 별도 연결 대상이다. 로컬 파일에 접근할 수 있다는 이유만으로 로컬 훅까지 작동한다고 가정하지 않는다.

## 2. 환경별 연결 계획

| 사용자 환경 | 상태를 받는 기본 경로 | 사용자에게 보이는 경로 | 완료 판정 |
|---|---|---|---|
| VS Code의 Codex 확장 및 지원되는 다른 IDE 확장 | 프로젝트의 공식 lifecycle hooks | 호스트의 hook 경고. 추가 표시 수단은 실제 지원 확인 후 선택 | 해당 확장 버전에서 실제 이벤트와 경고 표시 확인 |
| VS Code 내장 터미널의 Codex CLI | 같은 프로젝트 hooks | CLI의 hook 경고와 House 상태 조회 | 통합 터미널에서 별도로 확인 |
| 독립 터미널의 Codex CLI | 같은 프로젝트 hooks. 기존 House 실행 방식과 등록 중복 방지 | CLI 경고와 상태 조회 | 해당 OS·CLI 버전에서 확인 |
| 로컬 데스크톱 앱의 Codex 대화 | 앱이 실제 사용하는 로컬 실행 환경의 프로젝트 hooks | 앱의 hook 경고. 표시 미지원 시 그 사실을 명시 | 앱 버전·실행 환경별 실제 확인 |
| House 웹 UI | House가 소유한 app-server 연결 및 같은 경고 엔진 | 웹 경고 패널과 현재 상태 | 실제 서버 이벤트와 브라우저 표시를 함께 확인 |
| 클라우드가 대화를 운영하는 앱·웹 | 지원되는 공식 원격 이벤트 연결이 있을 때 별도 adapter | 허용된 원격 알림·클라이언트 경로 | 필요한 이벤트·식별·전달을 모두 확보해야 지원 판정 |

VS Code는 편집기이며, 그 안의 확장과 터미널은 서로 다른 실행 경로다. CLI에서 통과한 검사를 확장의 통과로 보고하지 않는다. 다른 회사의 모델·확장까지 자동 지원한다고 해석하지 않는다.

프로젝트 hooks를 기본 배포 경로로 선택한다. 플러그인은 선택 가능한 포장 방식으로만 둔다. 공식 문서 사이에 IDE 플러그인 지원 안내가 일치하지 않는 부분이 있어, 플러그인 설치만으로 모든 클라이언트가 연결됐다고 판정하지 않는다.

## 3. 공통 구조

    클라이언트의 실제 이벤트
      → 환경별 수신기와 기능 확인
      → 출처·프로젝트·대화 식별 및 공통 이벤트 변환
      → 하나의 House 경고 판단 엔진
      → 경고 기록과 전달 대기열
      → CLI / 확장 / 앱 / 웹의 표시 경로

연구 목표·설계·결과는 기존 프로젝트의 house/에 유지한다. 연결 설정과 관측 기록은 연구 계산의 입력·채택 기준을 바꾸지 않는다. 알림 판단을 위해 추가 모델을 호출하지 않는다. 인계 본문 작성은 기존 Main의 연구 작업으로 구분한다.

기본 연결은 상시 실행 서버를 요구하지 않는다. Codex의 lifecycle 이벤트가 발생할 때 짧은 로컬 명령을 호출한다. House 웹의 기존 서버는 그 서버가 소유한 연결에서 받은 이벤트만 처리한다. 다른 확장·앱이 소유한 app-server를 몰래 재개하거나 별도 Codex 프로세스를 띄워 대화를 빼앗지 않는다.

## 4. 연결 등록과 진단

아래 명령은 새로 제안하는 인터페이스이며 현재 0.4.1에는 없다.

    house connect --project <프로젝트> --dry-run --json
    house connect --project <프로젝트> --apply
    house doctor --project <프로젝트> --json
    house disconnect --project <프로젝트> --dry-run
    house disconnect --project <프로젝트> --apply

connect는 다음을 수행하도록 설계한다.

1. 실제 프로젝트·House pin·실행 환경·엔진 위치와 호스트 설정 계층을 확인한다. House가 초기화되지 않았다면 그 상태를 알리고, 단순 연결 등록을 연구 설계 합의로 취급하지 않는다.
2. 연결할 이벤트, 실행할 명령, 수정할 프로젝트 설정, 기존 hooks와의 병합 결과를 보여준다.
3. 승인된 연결 작업 범위 안에서 프로젝트 .codex/hooks.json에 House가 소유한 항목만 등록한다. 기존 inline hooks를 사용하는 프로젝트는 이중 표현을 새로 만들지 않고 충돌 없는 편집 계획을 선택한다. 사용자 훅은 삭제하거나 덮어쓰지 않는다.
4. 절대 실행 경로·명령·설정 전후 해시·소유 항목·원본 백업을 연결 영수증에 기록한다. 반복 실행은 같은 항목을 추가하지 않는다.
5. 호스트의 프로젝트 신뢰와 훅 신뢰가 필요함을 알린다. 사용자가 끈 훅을 켜거나 trust 검토를 우회하지 않는다. 이 확인은 Codex의 공식 훅 신뢰 절차이지 House가 파일마다 새 승인을 묻는 절차가 아니다.
6. 실제 callback을 받은 뒤 관측 연결 여부를 갱신한다. 설정 파일을 만들었다는 이유로 “활성화 완료”라고 보고하지 않는다.

설정을 변경해도 이미 열린 대화가 즉시 다시 읽는지는 별도 확인한다. 적용을 위해 호스트 재시작이 필요하면 현재 작업과 인계를 먼저 확인하고, 실행 중인 계산을 자동 종료하지 않는다.

disconnect는 영수증과 현재 파일을 대조해 House 항목만 제거한다. 설치 뒤 생긴 사용자 변경이 있으면 원본 파일 전체를 복구하지 않고 현재 변경을 보존할 수 있는 계획을 보여준다.

프로젝트 등록은 기본적으로 이 컴퓨터의 연결 설정이며 자동 commit·push하지 않는다. 새로 만든 로컬 설정과 영수증은 소스 공유 대상과 구분하고, 필요한 로컬 제외 설정도 dry-run에 포함한다. 이미 버전 관리 중인 hooks 파일에 컴퓨터별 절대 경로를 임의로 추가하지 않는다. 그 경우 공유 가능한 연결 명령과 환경별 로컬 바인딩으로 분리하는 편집 계획을 사용한다. 다른 컴퓨터에서 실행기·Python·바인딩이 없으면 경로 오류와 설치 필요 상태를 표시한다. 팀이 공유할 설정인지와 이 컴퓨터에서만 쓸 설정인지는 설치 영수증에 기록한다.

CLI의 연결 우선순위도 명시한다.

- 유효한 House project 등록의 명령·이벤트 집합·소유 영수증을 확인하면, 새 House CLI launcher는 같은 lifecycle hook을 invocation 설정에 다시 추가하지 않는다. 명시적으로 선택한 방은 launch 바인딩으로 project connector에 전달한다. 일반 대화는 Main으로 연결하며 폴더 이름만으로 방을 결정하지 않는다.
- project 등록이 없으면 기존처럼 invocation 범위의 세션 연결을 사용하되 같은 공통 adapter를 호출한다.
- 등록 충돌·정체 불명 항목·신뢰 미확정 상태에서는 두 경로를 동시에 켜서 해결하지 않는다. 충돌을 알리고 알림 연결은 미확정으로 남긴다. 에이전트 역할 정책·연구 계약 검사는 별개로 유지한다.
- 중복 방지는 이 우선순위와 공통 이벤트 식별을 함께 적용한다. 사용자 훅을 삭제하는 방법으로 중복을 숨기지 않는다.

진단 결과는 하나의 on/off 값으로 축약하지 않는다.

| 진단 항목 | 구분할 값의 예 |
|---|---|
| 설정 등록 | 없음 / 등록됨 / 충돌 |
| 호스트 지원 | 확인됨 / 미확인 / 미지원 |
| 훅 실행 신뢰 | 확인됨 / 검토 필요 / 비활성화 / 조회 불가 |
| 이벤트 수신 | 미관측 / 최근 수신 / 연결 중단 또는 관측 지연 |
| 문맥 사용량 | 최근 관측값·시각·출처 / unknown |
| 압축 집계 | 자동·수동·분류 불가 / 집계 시작 범위 |
| 알림 전달 | 대기 / 호스트에 출력 / 호스트 수락 확인 / 화면 확인 / 불명 |

호스트 API가 훅 목록·신뢰 조회를 제공하지 않으면 해당 필드는 unknown으로 남긴다. 실제 callback으로 입증되는 부분만 별도로 기록한다.

## 5. 이벤트 수신과 사용량

기본 등록 대상은 SessionStart, UserPromptSubmit, PostToolUse, PostCompact, Stop이다. 알림 연결에는 방별 에이전트 제한용 PreToolUse 정책을 섞지 않는다. 확장이나 앱의 일반 도구 사용을 세션 알림 때문에 제한하지 않는다.

기존 대화에 연결할 때 시작 이벤트를 놓쳤을 수 있다. 첫 실제 callback의 대화 식별자와 transcript로 관측을 시작하는 attach 경로를 별도로 구현한다. 과거 SessionStart를 받았다고 기록하거나 이전 압축 횟수를 추정하지 않는다.

공통 이벤트에는 다음 정보가 필요하다.

    schema_version, project_id, execution_environment_id
    conversation_key, native_thread_id, native_session_id
    parent_thread_id, agent_id, transcript_source
    kind, native_event_id, source, occurred_at, observed_at
    context_usage, compaction_trigger, identity_evidence

제공되지 않은 필드는 null과 이유로 남긴다. 종류는 attached, usage_observed, compaction_completed, boundary_saved, delivery_observed 등으로 구분한다. 이벤트 변환기는 과학적 판단이나 새 사용자 동의를 만들어내지 않는다.

데이터 출처의 우선순위는 다음과 같다.

1. House가 적법하게 소유·구독하는 app-server의 공식 구조화된 이벤트. 설치된 버전의 스키마를 확인하고 해당 값이 현재 문맥 점유량을 의미하는 경우에만 70% 판정에 사용한다.
2. native hook이 제공하는 실제 대화 정보와, 버전 검증된 제한적 transcript adapter. 현재 0.4.1의 최근 token_count 파서는 이 경로에 해당한다.
3. 어느 경로에서도 필요한 값을 얻지 못하면 unknown.

누적 청구 토큰을 현재 문맥 사용량으로 대체하지 않는다. 관측 시각·계산에 사용한 분자·문맥 한도·출처를 보존한다. 오래된 수치를 실시간 사용량처럼 표시하지 않고, 압축·모델/한도 변경 뒤에는 새 관측이 확보될 때까지 이전 비율을 무효화한다.

app-server의 contextCompaction 완료는 압축 발생 근거가 될 수 있지만, 문서의 해당 item만으로 자동/수동을 분류할 수는 없다. 자동 압축 횟수에는 PostCompact(trigger=auto) 등 검증된 원인을 함께 확보한 이벤트만 포함한다. 원인 불명 이벤트는 별도 집계하고 자동 압축으로 추정하지 않는다.

## 6. 대화·프로젝트 식별과 중복 방지

- 프로젝트 연결 시 생성한 project_id와 실제 소유 환경을 사용한다. 경로 이름이나 “가장 최근 세션”으로 프로젝트·대화를 고르지 않는다.
- native thread ID를 확보한 대화는 프로젝트·실행 환경·thread ID로 식별한다. native session ID가 같다고 fork나 하위 대화를 합치지 않는다.
- hook에 thread ID가 없으면 실제 session ID·transcript 관계로 임시 관측 스트림을 만들고 미확정임을 기록한다. 공식 식별 근거를 얻기 전에는 다른 스트림과 병합하지 않는다. 로컬 관측 키를 native chat ID라고 부르지 않는다.
- resume는 동일 대화의 상태를 이어간다. 새 대화와 fork는 별도 문맥 상태와 압축 횟수로 시작하고, 이전 인계는 근거 경로로 연결한다. Main과 자식 에이전트의 관측은 분리한다.
- 이벤트 고유 ID 또는 검증된 압축 기록의 식별 근거로 중복을 제거한다. turn ID 하나만으로는 같은 턴의 여러 압축을 구분할 수 없다.
- 동일 이벤트가 project hook, 기존 House CLI hook, 웹 adapter로 반복 들어와도 한 번 처리한다. 서로 같은 사건임을 입증할 수 없는 압축은 “중복 여부 불명”으로 보관하며 확정 10회 집계에 넣지 않는다.
- 둘 이상의 클라이언트가 같은 대화를 보더라도 관측·경고 기록은 공유한다. 별개 대화를 동시에 수행하는 것은 허용하되 같은 대화에 명령을 보내는 제어권은 기존 소유 클라이언트에 둔다.

기존 세션 기록과 새 관측 키를 연결하는 전환 규칙:

- 현재 room/sessions/<session-id>/ 아래의 session.json, events.jsonl, token floor, compact keys, handoff와 snapshot은 원본 경로·해시와 함께 보존한다.
- 새 연결 상태·식별 매핑은 house/main/integration/v2에 별도로 기록한다. 새 스키마 적용을 기존 과학적 입력·결과 migration과 묶지 않는다. 기존 pin이나 과거 run 기록도 바꾸지 않는다.
- 실제 native 식별과 transcript 관계를 검증한 경우에만 기존 대화로 연결한다. 이름·시각·session ID 하나만 맞는 fork·하위 대화는 자동 병합하지 않는다. 매핑 영수증에 출처·검사 시각·이전 상태 해시를 남긴다.
- 새 상태 조회는 구버전 집계와 새 연결 이후 집계를 각각 보여준다. 검증 가능한 동일 사건만 계승하고, 확인할 수 없는 과거 횟수는 unknown으로 표시한다. 기록을 숨긴 채 횟수를 0으로 초기화한 것처럼 보이게 하지 않는다.
- 과거 checkpoint는 해시를 검증해 연결한다. 이미 새 대화 권고가 기록된 동일 대화는 그 이력을 보존하여 새 연결 때문에 다시 권고하지 않는다. 이전 화면 전달 여부는 별도로 unknown일 수 있다.

저장 범위는 다음처럼 고정한다. house/main/integration/v2는 상태 소유 환경에서만 사용하는 로컬 runtime 영역이며 자동 track/save와 소스 공유에서 제외한다. 연결 영수증·실행기 절대 경로·OS별 바인딩은 HOUSE_HOME/runtime/connections/<project-id>/<environment-id>/에 보관한다. 프로젝트에 공유할 것은 project_id, 명시적 정책, 확인된 인계·결과 근거이며 컴퓨터별 절대 경로나 endpoint 자격 정보를 공유 설정에 넣지 않는다. 이 경계를 track/save와 설치 회귀 검사에도 반영한다. 다른 환경의 연결은 명시적 바인딩으로 소유 환경에 접근하고, 소유 runtime에 접근하지 못하면 기존 횟수를 복제하거나 추측하지 않는다.

압축 집계의 변경 제안도 구분한다. 0.4.1은 식별 근거가 없는 유효 PostCompact 전달도 각각 세므로 replay가 중복 집계될 수 있다. 새 설계는 자동 전달 관측 수와 식별 가능한 자동 압축 수를 나누고, 확정 10회 판정에는 후자를 쓰도록 제안한다. 이는 중복 안전성을 높이는 집계 의미의 정밀화이며, 기존 동작과 같다고 주장하지 않는다. 구현 전 정책 확인과 별도 회귀 검사를 거쳐 채택하며 과거 카운터를 새 의미로 소급 변환하지 않는다.

## 7. 경고 규칙과 전달

70%에서 인계를 준비하고 자동 압축 10회 이후 저장된 작업 경계에서 새 대화를 권한다는 운영 목적을 유지한다. 집계 근거를 정밀화하는 변경 제안은 앞 절과 같이 별도로 구분한다.

| 조건 | 행동 |
|---|---|
| 최근 유효 문맥 관측이 70% 이상 | 해당 문맥 구간에서 인계 준비 경고 생성 |
| 완료된 자동 압축 | 횟수 갱신과 목표·결정·진행 중 작업·다음 행동 재확인 안내 |
| 자동 압축 10회 이상 + 실제 작업 경계 + 유효 인계 저장 | 해당 대화에서 새 대화 권고를 한 번 생성 |
| 수동 압축 / 원인 불명 압축 | 자동 압축 10회 기준에 포함하지 않음 |
| 단순 Stop / 10회 도달만 발생 | 새 대화 권고 조건으로 삼지 않음 |
| 경과 시간만 증가 | 대화를 끝내거나 계산을 멈추지 않음 |

인계는 실제 내용이 있는 네 절과 8,000자 제한을 유지하고 snapshot 해시로 고정한다. 새 대화는 인계를 읽은 뒤 현재 파일과 실행 상태를 확인한다. 알림은 채팅 종료·실험 중단·모델 변경·새 모델 턴 생성 명령을 발행하지 않는다.

경고 생성과 전달 완료를 분리한다. alert_id와 생성 근거를 먼저 저장하고 각 표시 경로의 전달 상태를 별도로 관리한다. “한 번 출력할 예정” 플래그만 먼저 저장한 뒤 응답이 소실되어 알림이 영구히 사라지는 구조를 피한다.

CLI·IDE·앱은 native hook 출력의 systemMessage를 기본 경로로 사용한다. 모델이 인계를 준비할 수 있도록 해당 이벤트가 지원하는 additionalContext도 전달한다. House 웹에는 동일 alert_id의 명시적 경고 패널을 추가한다. 현재 웹의 비율 숫자만 표시하는 것으로 70% 알림 구현을 완료했다고 보지 않는다.

stdout에 경고 JSON을 썼다는 사실과 실제 사용자가 화면에서 봤다는 사실은 다르다. 호스트 수락 이벤트나 UI 확인이 없으면 화면 표시 상태를 unknown으로 남긴다. 재전달은 같은 alert_id로 제한하고, 인계 준비 경고와 새 대화 권고를 무제한 반복하지 않는다. 호스트에 표시 확인 API가 없는 경로에서 정확히 한 번의 화면 표시를 보장한다고 주장하지 않는다.

여러 클라이언트의 전달 경쟁은 다음 규칙으로 처리한다.

- 경고는 대화당 하나의 alert_id를 가진다. 각 표시 경로는 endpoint_id를 갖고 경고·표시 경로별 전달 기록을 둔다. 하나의 CLI가 출력했다는 이유로 앱의 전달 기록까지 완료 처리하지 않는다.
- 같은 endpoint로 들어오는 동시 callback은 짧은 전달 lease로 한 호출만 출력한다. 전송 실패가 명확하면 lease를 반환하고 같은 alert_id로 재시도한다.
- lease가 만료됐더라도 출력 성공 여부가 불명확하면 “미전달”로 단정해 매 도구 호출마다 다시 경고하지 않는다. 상태 조회에는 계속 남기고, 새 사용자 요청 시점이나 명시적 재표시 요청에서 같은 경고를 제한적으로 전달한다.
- 각 화면이 같은 대화를 실제로 보고 있다면 화면별 한 번의 전달 시도는 허용한다. 수신 확인 기능이 있는 화면은 alert_id로 중복 표시를 제거한다. 확인 기능이 없는 native 화면은 전달 시도·호스트 수락·사용자 표시 확인을 구분한다.

운영체제 소리·데스크톱 팝업은 선택 기능으로 별도 설계한다. 핵심 수용 기준은 작업 화면의 텍스트 경고이며, OS 알림 권한이나 집중 모드 때문에 핵심 경고가 사라지게 하지 않는다.

## 8. Windows·WSL·macOS·Linux

설치 위치와 Codex가 실제 실행되는 환경을 함께 기록한다. Windows의 앱, WSL의 Codex, 원격 Linux의 확장이 같은 실행 환경이라고 가정하지 않는다.

현재 storage.py는 POSIX flock만 지원한다. Windows native 지원에는 락·경로·실행기·설치 방식을 먼저 보강해야 한다.

| 영역 | 설계 요구 |
|---|---|
| 락 | POSIX와 Windows용 명시적 backend. 실제 Windows 동시성 시험 필수. 락 실패를 성공으로 무시하지 않음 |
| 실행기 | POSIX 실행기와 Windows용 실행기 생성. Python 경로·공백·한글·명령 인수는 OS에 맞게 처리 |
| 설치 | Windows에서 관리자 권한 symlink를 필수로 두지 않는 관리 가능한 설치 방식 |
| 이벤트 읽기 | transcript를 생성한 실제 환경에서 읽고, 다른 OS의 절대 경로를 자기 경로로 해석하지 않음 |
| 프로젝트 상태 | 동일 프로젝트 관측의 소유 환경을 명시하고 쓰기를 그 환경에서 직렬화 |

Windows 앱과 WSL Codex가 같은 프로젝트를 쓰는 경우는 두 단계로 지원한다.

1. 각 환경의 수신기가 자기 환경에서 관측값을 읽는다. 명시적으로 매핑한 동일 project_id와 대화의 native 관계만 전달한다.
2. 한 환경을 관측 상태의 소유자로 지정한다. 다른 환경은 검증된 명령 전달 경로로 정규화된 이벤트를 보내고 경고 응답을 받는다. 예를 들어 Windows → WSL은 지정된 배포판의 wsl.exe --exec 호출로 연결할 수 있다. 새 Codex를 실행하는 용도로 쓰지 않는다.

직접 혼합 쓰기 방식은 Windows와 Linux의 락이 같은 파일시스템에서 상호 작동함을 입증하기 전에는 지원하지 않는다. 환경 간 경로 매핑·전달 수단이 없으면 연결 불가 이유를 표시한다. 동일한 이름의 폴더를 임의로 같은 프로젝트로 취급하거나, 감시가 된다고 보고하지 않는다.

## 10. 구현 순서와 완료 기준

1. 공통 이벤트·경고 상태와 전달 기록을 정의하고, 기존 70%/10회 의미를 보존하는 회귀 검사를 만든다.
2. project connect/doctor/disconnect와 이미 열린 대화의 attach를 구현한다. 설치·조회와 실제 이벤트 수신을 구분한다.
3. WSL/Linux CLI, VS Code 통합 터미널, VS Code Codex 확장을 각각 확인한다. 이 셋을 한 번의 CLI 검사로 대체하지 않는다.
4. macOS/Linux 데스크톱 로컬 앱과 Windows native 지원을 구현·검증한다. Windows/WSL 혼합 소유권 전달을 별도 검사한다.
5. House 웹도 같은 공통 이벤트·경고를 사용하도록 연결한다. 모델 호출 없이 가능한 경고 전달 검사를 먼저 수행한다.
6. 각 대상의 실제 설치 버전·OS·실행 환경·관측 이벤트·경고 표시 근거를 지원 표에 기록한다.

핵심 수용 검사:

- 69% / 70% / 반복 관측 / 압축 뒤 재경고 / 사용량 누락·잘못된 한도·오래된 관측.
- 자동 9회 / 자동 10회 / 수동·분류 불명 제외 / Stop·일반 저장 제외 / 경계와 유효 인계가 있을 때 한 번 권고.
- 새 대화·resume·fork·자식 에이전트의 상태 분리와 인계 연결.
- 여러 클라이언트·여러 hook 경로의 동일 이벤트, 같은 턴의 복수 압축, 식별 불가능 replay.
- 경고 저장 직후 전달 실패, 프로세스 재시작, 동시 파일 갱신과 락 충돌.
- 다른 사용자 hooks 보존, 반복 설치, 설정 변경 뒤 해제, 신뢰 거부·비활성화 존중.
- Windows 경로·공백·한글·실제 Windows 락, WSL 경계, project_id 소유 환경 불일치.
- 실제 클라이언트 callback과 실제 경고 UI. synthetic 데이터 검사, native 훅 전달 검사, 실제 장기 대화 시험을 서로 다른 검증 수준으로 기록.

일반 모델 작업을 길게 반복해 일부러 자동 압축 10회를 만들지 않는다. 임계치 로직은 합성 시험, 실제 hook/UI 경로는 명시적으로 표시한 제한적 연결 시험으로 확인하고 실제 장기 운영 검증과 구분한다. 기존 계산과 사용자 작업은 보존한다.

모든 행은 “설계 대상 / 구현됨 / 재현 시험 통과 / 실제 클라이언트 확인 / 장기 운영 확인”을 따로 기록한다. 아직 시험하지 않은 OS·앱을 통과로 표시하지 않는다. 공식 이벤트 접근이 없는 클라우드 환경은 자동 경고 지원 완료 대상에 넣을 수 없으며, 지원 불가 조건과 필요한 공식 기능을 공개한다.
